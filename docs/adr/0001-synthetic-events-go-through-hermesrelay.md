# ADR-0001: Synthetic events go through hermesrelay (not a side channel)

> **Status**: Accepted — implementation verified end-to-end on `rebuild` branch (2026-05-12)
> **Date**: 2026-05-12
> **Context**: M5 (Hermes-first), task 5.3 inter-NPC messaging
> **Supersedes**: —
> **Related**: [`docs/hermes-event-trigger.md`](../hermes-event-trigger.md) (locked Plan B), `docs/events.md`, `docs/roadmap.md` 5.3 / 5.6 / 5.13

---

## Context

M5 task 5.3 added three inter-NPC messaging tools to `smartnpc-mcp`:

- `npc_send_message` — A → B private message, queued in an in-memory mailbox
- `npc_broadcast_event` — A → all fire-and-forget signal
- `npc_inbox_get` / `npc_inbox_ack` — pull-side mailbox API

The fan-out path (`emitSyntheticEvent` in `internal/tools/npc_message.go`)
emitted these as **MCP logging notifications only**, mirroring the
envelope `tools.MakeEventForwarder` uses for SMAPI mod events.

This was the right shape for Hermes profiles consuming events as MCP
notifications (the original Plan A from
[`docs/hermes-event-trigger.md`](../hermes-event-trigger.md)). However,
5.0b locked **Plan B**: Hermes does not consume MCP notifications as
agent triggers; instead `smartnpc-mcp` POSTs events to the Hermes Gateway
via `internal/hermesrelay/`.

The relay is wired into `cmd/smartnpc-mcp/main.go::makeRouter`, which
sits on the **WebSocket inbound path** from the SMAPI mod. Synthetic
events generated by tool calls never traverse that path — they go
straight from the tool handler to MCP `Sessions().Log()`.

Symptom: NPC A delegates to NPC B via `npc_send_message`. The mailbox
queues the message and the MCP notification fans out to any subscribed
client, but B's Hermes profile is never POSTed and B does not wake.

## Decision

Synthetic events emitted by `smartnpc-mcp` itself (currently
`npc_message`, `npc_broadcast`; future inter-NPC events follow the same
rule) are routed through the **same `bridge.EventHandler` chain** that
mod-sourced events traverse. There is no separate hermesrelay invocation
for synthetic events; they reuse the existing `makeRouter` → `relay` /
`group.Dispatch` plumbing.

### Wiring

A `bridge.EventHandler` reference is constructed in `main.go` (the same
closure that wraps `MakeEventForwarder` + `relay`) and threaded through
`tools.RegisterAll(...)` into `registerNpcMessage(...)`. The synthetic
event emitter calls **both**:

1. `server.Sessions().Log(...)` — preserves backward compatibility for
   any MCP notification consumer (dev harness, future tooling).
2. The shared `bridge.EventHandler` — feeds the event into the same
   audible-routing / hermesrelay / group-dispatch pipeline mod events
   use.

This is a hook injection, not a re-architecture: `RegisterAll` gains one
parameter; `registerNpcMessage` closes over it; `emitSyntheticEvent`
gains one extra call. No new package, no new transport, no new
goroutine pool.

The handler value passed in is the **same** `hermesHandler` instance
`main.go` already constructs for the ws-router path (built once from
`--hermes-config` group dispatcher or legacy single-target relay,
re-used for both consumers). This identity — not just type
compatibility — is the concrete realization of the "single outbound
egress" property in alternative A's rejection and the Positive
consequence list below.

`npc_broadcast_event` rides the same path for free: its tool handler
already calls `emitSyntheticEvent`, so `match.npc`-less broadcast
events are delivered to every routed Hermes profile through the
existing `group.Dispatch` fan-out — no broadcast-specific wiring
required. This consistency reinforces points (a) and (c) in the
"Alternatives — A. Separate outbound path" rejection.

### Context detachment (load-bearing)

`emitSyntheticEvent` invokes the shared handler on a **detached
context** (`context.Background()` in a `go` statement), not the MCP
request `ctx`.

> **Why this matters — do not "fix" this back to request ctx.**
> The MCP SDK cancels the request context as soon as the tool handler
> returns its `(result, output, error)` triple. `Relay.post` issues an
> async `http.Client.Do(req.WithContext(ctx))` — if the request ctx is
> wired through, the cancellation propagates to the in-flight HTTP POST
> and the Hermes Gateway sees a `context canceled` mid-flight, dropping
> the trigger. The mod-event path doesn't have this problem because the
> ws read loop owns its ctx for the entire connection lifetime.
>
> Concretely: A's `npc_send_message` returns `OK=true` to A's profile,
> A's turn ends, ctx cancels, B's POST is dropped by the HTTP client.
> The bug looks identical to "synthetic event was never emitted" —
> hence this paragraph.
>
> Reviewers: if you see `context.Background()` here and reach for `ctx`,
> first re-read this ADR and the test that pins this behavior.

## Alternatives considered

### A. Separate outbound path for synthetic events

Spin up a second `Relay` (or call `Relay.Forward` directly) inside
`emitSyntheticEvent`, bypassing `makeRouter`.

Rejected because:

- **Two outbound egress points** double the surface for rate-limiting,
  retry, and observability. We'd need to duplicate `match.npc` routing
  config, or risk drift between the two paths.
- The audible-routing logic in `makeRouter`
  (`synthChatMessageFromAudible`) has nothing to do with synthetic
  events today, but the **structural symmetry** of "every event the
  relay sees, regardless of origin, has gone through one router" is
  worth preserving for future event types.
- `events.IsMod` / `events.IsSynthetic` already give the relay enough
  metadata to apply per-source policy if it ever needs to. No
  architectural reason to split the pipe.

### B. Make the tool handler call the Hermes Gateway directly

Skip the MCP layer entirely; have `npc_send_message` POST to Hermes
inline.

Rejected because:

- Couples a tool implementation to a transport protocol. The whole
  point of `hermesrelay` is to keep the "where do events go" decision
  in one place.
- Loses the MCP notification fan-out for free (any non-Hermes consumer
  goes dark).
- Tool latency would now include synchronous Hermes RTT.

### C. Status quo (notification-only) + add a Hermes-side poller

Have Hermes profiles poll `npc_inbox_get` on a cron.

Rejected because:

- Defeats real-time inter-NPC delegation, which is the whole point of
  `npc_send_message` over a passive mailbox.
- Adds latency proportional to poll interval; M5 wants delegation to
  feel conversational, not eventual.
- The mailbox is meant as a **catch-up mechanism** for missed
  notifications, not the primary delivery channel.

## Consequences

### Positive

- One outbound egress for all event types — single place for rate
  limiting, retry, metrics, auth headers.
- `match.npc` routing in `hermes/runtime-config.yaml` works for
  synthetic events without a second config block.
- A → B delegation Just Works: A's `npc_send_message` triggers B's
  Hermes profile via the same code path as a player chat would.
- Test surface stays small: `pipeline_test.go`'s existing
  fake-gateway harness validates synthetic + mod events with the same
  fixtures.

### Negative / risks

- `RegisterAll` signature changes — every test or external caller
  constructing the tool registry must pass the new handler (or `nil`
  for "synthetic-events-only-as-MCP-notification" mode in unit tests).
  Mitigated by accepting `nil` and falling back to log-only when no
  handler is wired.
- Synthetic events now incur whatever latency / failure modes the
  hermesrelay HTTP client has. Mitigated by the existing
  fire-and-forget goroutine pattern (`go r.post(...)`); the tool
  handler returns immediately regardless of POST outcome.
- Future ctx-discipline lapse could re-introduce the request-cancel bug
  silently. Mitigated by the ctx-detachment paragraph above and a
  pinned test (qa-tester).

## Implementation notes

> File-level anchors (function/identifier names) are stable; absolute line numbers shift with formatter passes, so prefer the anchors when grepping. Verified against `rebuild` working tree at 2026-05-12 pre-commit.

- **`smartnpc-mcp/internal/tools/registry.go::RegisterAll`** — signature
  gained an `hermes bridge.EventHandler` parameter ahead of `logger`,
  threaded into `registerNpcMessage`. Doc-comment in-file calls out
  "same `bridge.EventHandler` used for forwarding mod events".
- **`smartnpc-mcp/internal/tools/npc_message.go::registerNpcMessage`** —
  accepts the handler and closes over it; both `npc_send_message` and
  `npc_broadcast_event` tool handlers pass it down to
  `emitSyntheticEvent`.
- **`smartnpc-mcp/internal/tools/npc_message.go::emitSyntheticEvent`** —
  after the existing `server.Sessions()(...)` MCP-notification block,
  the function ends with `if hermes != nil { go hermes(context.Background(), name, data) }`.
  The `context.Background()` here is the load-bearing detachment from
  the tool-call ctx — see "Context detachment (load-bearing)" above.
- **`smartnpc-mcp/cmd/smartnpc-mcp/main.go`** — call site is
  `tools.RegisterAll(server, br, hermesHandler, logger)`. The
  `hermesHandler` value is the **same** closure already used by ws-side
  routing (built once from `--hermes-config` group dispatcher or the
  legacy single-target relay, then passed to both consumers). This
  identity — not just type compatibility — is the concrete evidence for
  the "single outbound egress" claim in the Decision section.
- **Tests**: `internal/tools/npc_message_hermes_test.go` (new, pins the
  detached-ctx + handler-invocation contract) and the existing
  `cmd/smartnpc-mcp/pipeline_test.go` "synthesized chat_message"
  fixtures cover the happy path; `pipeline_test.go` extension for an
  inter-NPC delegate flow is captured in qa-tester's E2E checklist
  rather than as a separate unit test.

## Verification

This ADR is verified together with M5 5.6 / 5.7 / 5.13(delegate) in one
end-to-end run (see `docs/manual-e2e-verification.md`):

1. Player → NPC A: "go fetch B for me".
2. A's profile calls `chat_say` + `npc_send_message(to=B)`.
3. Hermes Gateway receives a POST tagged `conversation: B`.
4. B's profile wakes and responds in-character.

When this passes on real hardware, flip `docs/roadmap.md` 5.6 / 5.7 /
5.13 from 🧪 to ✅ and update this ADR's status to **Accepted**.
